# play/agent_sft

**Nudge-grounded SFT**: Use the `require_tool` closed loop of [`play/agent_engine`](../agent_engine/) as a supervision signal, and perform LoRA/QLoRA fine-tuning on the local model, so that "it is only called by nudge" as much as possible becomes "corrected the first time". The training pipeline is: mine traces → SFT on (failed turn, nudge, corrected turn) → retest with [`play/evals`](../evals/). The historical v1 (Qwen2.5-7B) has passed GGUF + Ollama; the current v1.6 (qwen3.5:9b) training and evaluation has been passed, but the real deployment of GGUF / Ollama is still blocked by Qwen3.5 hybrid runtime garbled code.

## Central question

> Taking "`agent_engine` has to emit nudge" as the **own supervision signal** as the fine-tuning target, can a 7B/9B-class local model significantly reduce the nudge-fire rate on its own output trajectory without regression on OOD tool calls?

This isn't "do it again BFCL fine-tune" - too many people have walked that road. The difference of this project is: **supervision signal can only be generated by my own agent system**, and the recurrence threshold is the moat.

> **Engineering Constraints** (not going into the central question): Standalone M4 Pro 48GB. v1 uses Qwen2.5-7B QLoRA to prove that the method is effective; v1.5 / v1.6 follows the default base of the warehouse and migrates to qwen3.5:9b. The central question is not tied to a specific model, but asks: "Can the own nudge signal stably improve the own agent trajectory?"

### Report dimensions (just follow this when implementing evals task wrapper in Phase 1 to avoid having to add it in Phase 5)

In addition to the aggregation number, each metric must be broken down according to the three axes + multiple seeds in the table below. This layer of structure is the input of v2-C "Failure Mode Taxonomy + Difficult Sample Mining". Implementing it before Phase 1 can avoid the discovery that "no fine-grained data is stored and needs to be rerun" during the Phase 5 retest.

|Axis|Split|Why|
|---|---|---|
|**per-scenario**|Group by `agent_engine` scenario files|Locate "which scenario is the most difficult" - can be used as a starting point for hard sample mining|
|**per-tool**|Group by `require_tool` name (`cast_vote` / `write_section` / ...) | Locate "which tool is most likely to miss adjustments" - can be used for targeted data enhancement signals |
|**per-failure-mode**|Classified by error type: missed adjustment/wrong adjustment (other tools were adjusted)/Parameter error (correct adjustment but wrong args)|Failure mode taxonomy reserved - v2-C candidate input|
|**Multiple seeds**|Each group ≥ 3 seeds, report mean ± standard deviation|LLM output is random, single run numbers are not credible, and the confidence interval is the minimum standard for S-level portfolio|

## Lessons learned (v1 case closed)

All seven stages of v1 passed, 120 runs (3 model × 4 task × 10 seed) end-to-end retest, **[`DECISIONS §9`](DECISIONS.md#9-v1-closure phase-5-digit three threshold hit--v2v3-candidate selection) passed all three thresholds** → Central question [`§1`](DECISIONS.md#1-nudge-grounded-sft-as the central question of the project) "Using its own `require_tool` nudge as supervision, can 7B significantly reduce the nudge-fire rate on its own trajectory without OOD regression?" The answer is **"Yes, but there are boundaries"**. The most noteworthy thing is not the 57.3% gap closure number itself, but three things: ① nudge SFT converts `missed` (missing adjustment) errors into `wrong_tool` (misadjusted) errors, rather than eliminating them all; ② `agent_traj.task_success` SFT (1.00) **overtakes** 32B ceiling (0.93), but `trajectory_match` degrades by 31% - the task is completed, but the path deviates gold; ③ `by_tool.retrieve_docs` SFT 100% requires nudge, which is the price of [`§4`](DECISIONS.md#4-sft-target-schema-with-openai-tool_calls--top-level-tools-fields qwen25-native) drop 250 retrieve_docs no-template samples. These three things have drawn the first targets for v2-B (on-policy)/v2-C (hard sample mining).

Two lessons are collected at the methodology level: ① **Fast proxy is bound to be saturated in schema learning**——[`§5`](DECISIONS.md#5-phase-3-recommended-adapter-lock-base-configuration layersrank-sweep--true effect decision is postponed to-phase-5) The locked "`eval_smoke` 4 indicators are all 100% and do not prove that SFT is effective" in Phase 5 During the end-to-end retest, it was disproven: while the proxy was all 100%, the end-to-end `nudge_fire_rate` only had a gap of 9.4 percentage points. The cost of `evals` running ~50 min/run × 32B × agent-path cannot be saved. ② **The fragility of the evaluation harness itself is a by-product of Phase 5** - `qwen2.5:7b seed=3` spontaneously outputs `tool=cast_vote(...)` illegal kwarg → `agent_engine` and directly `TypeError` causes the entire batch run to hang. Although the loss of 1/120 data points is small, it exposes the lack of defense of evals/agent_engine in the face of LLM "abnormal output"; it is written into the [`agent_engine`] backlog and will not be repaired in this project.

## Interview narrative script (v1 closed version)

> "I wrote an agent engine myself, which has a `require_tool` mechanism: when a certain tool must be called at a certain step but LLM misses the adjustment, the engine will send a nudge signal to let it try again. This nudge signal is free supervision-it originally means whether the model should be adjusted or not. I used it as the target of SFT, dug out about 1k (failed turn, nudge, corrected turn) triples, and used MLX-LM QLoRA on M4 Pro 48GB Fine-tuning Qwen2.5-7B.
>
> How do you know it works? I used the evals harness I wrote (lm-eval-harness style, with phase-5 trajectory eval) to run 3 model × 4 task × 10 seed = 120 runs. Three sets of comparisons: original Qwen 7B / my fine-tuned 7B / Qwen2.5-32B original version (same family, cross-scale ceiling reference). **nudge-fire rate dropped from 0.739 to 0.645, closing the 57% gap** with the 32B homologous ceiling (0.575); BFCL public slice regression 1.2%, MMLU subset regression 2.1%, all within the pre-locked threshold. In v1, fine-tuning the weight can also be fused into GGUF and registered as a local Ollama tag; this step is temporarily blocked after the migration of qwen3.5. The current `agent-sft-qwen-3` is a placeholder and cannot be used to represent the adapter effect.
>
> But what is more interesting than the numbers is the 'reverse of the coin' behind the numbers: SFT **didn't** eliminate all the 'missed tuning' errors, but **converted** them into 'wrong tuning' - the model learned 'the tuning' but not yet learned the 'right tuning'. Moreover, SFT surpassed 32B in end-to-end task success (1.00 vs 0.93), but the alignment of trajectory and gold sequence degraded by 31% - the model won by taking more "detours". These two things neatly put the two candidates for v2 - on-policy iterative SFT and failure mode hard sample mining - into the target.
>
> The most noteworthy thing about this project is not the 57% gap number, but that the supervision signal can only be generated by my own agent stack. **The entire link is all local and has zero closed source dependencies** - no other portfolio can replicate this; and each 'back of the coin' can be linked to a specific ADR ([`DECISIONS §9`](DECISIONS.md#9-v1-case closing phase-5-digit three threshold hit--v2v3-candidate selection)), it is not a negative finding that is written and forgotten. "

## Appendix 1: Full spectrum of model tuning

Flatten all the means of "making an existing model more suitable for my task" into a table, and sort them from light to heavy (A → H) according to "change the weight or not / how much to change". **SFT ⊂ fine-tune ⊂ Model Tuning** - This project falls into the combination of D's "SFT" + B's "QLoRA" + H's "GGUF/Ollama". Various types can be stacked (PEFT + SFT + DPO is a common combination).

Let’s first look at what each category does, and then drill down to the specific methods:

|Category|Brief explanation|Typical representative|
|---|---|---|
|A. Inference-time/prompt-time tuning|Don't move the model, just focus on "how to ask" - change the prompt, plug in examples, and add external materials/tools. Cheapest, first to try |Prompt engineering / RAG / Tool use|
|B. PEFT bypass (parameter-efficient fine-tuning)|The main model is frozen, and only a very small "plug-in" (adapter / low-rank matrix / soft prompt soft prompt) is trained next to it. Like adding a removable lining to a suit - it can be changed and saves video memory|LoRA / QLoRA / Adapter|
|C. Partial FT (partial fine-tuning)|Between PEFT and Full FT - only unfreeze a part of the layers for training. Today mostly replaced by PEFT|Layer freezing / BitFit|
|D. Full FT (full fine-tuning)|Update the entire model weights. The upper limit of capabilities is the highest, but the threshold of video memory/data/computing power is also the highest, and it is prone to catastrophic forgetting |SFT/CPT/DAPT|
|E. Preference alignment/RL (preference alignment/reinforcement learning)|Does not give a "standard answer", but only tells the model "which of the two answers is better". The mainstream approach to teaching manners, values, and human alignment |RLHF / DPO / GRPO |
|F. Self-improvement/self-distillation|Training data is produced by the model itself (or a model of the same family) - sampling, filtering, and self-scoring (bootstrap). supervision does not rely on manual labor|Rejection sampling / STaR / Self-Refine|
|G. Model merging / editing (model merging / editing) | No training data required - directly do arithmetic (merging, addition and subtraction) on several existing weights, or surgical edit to change one or two facts | TIES merging / Task arithmetic / ROME |
|H. Deployment tuning/inference optimization|The purpose is not to make the model smarter, but to make it smaller and faster to go online - quantization, pruning, and distillation to a small model|GGUF / AWQ / GPTQ / pruning|
